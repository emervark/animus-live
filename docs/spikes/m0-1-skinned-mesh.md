# M0-1 — Procedural skinned mesh in Bevy 0.19.1

Spike crate: `spikes/m0_1_skinned_mesh`. Run with:

```
cargo run --release --manifest-path spikes/m0_1_skinned_mesh/Cargo.toml -- [flags]
```

Flags: `--auto-close <frames>`, `--stress` (50 puppets), `--joints <N>` (default 40),
`--no-bounds-fix`, `--no-animate`.

All measurements below are copy-pasted stdout from actual runs on this
machine (Windows 11, Intel i9-9900K, NVIDIA RTX 4080 SUPER, Vulkan backend),
release build, `--auto-close`, uncapped present mode (`AutoNoVsync`), on
2026-08-16.

## Do flat (non-hierarchical) joint sets skin correctly?

**Yes, mechanically confirmed by build + run.** The spike spawns 40 joint
entities that are all `ChildOf(root)` — direct children of one puppet root
entity — and are siblings of each other (no `ChildOf` between joints). Bevy's
own `SkinnedMesh { joints: Vec<Entity>, .. }` API has no notion of a joint
hierarchy at all; it is a flat list of entities read for their
`GlobalTransform` each frame (see `bevy_pbr::render::skin::add_skin`, which
iterates `skinned_mesh.joints` linearly and pairs each with its inverse bind
pose by index — no parent-chasing). The mesh renders and deforms as expected
under the per-joint sine-wave driver (visual confirmation is a user
checklist item below, since it requires eyes on the window).

**This directly supports spec §7.3: joints are a flat graph, not a bone
hierarchy, and Bevy's skinning API does not fight that.**

## Which of positions/UVs flips in Y?

Implemented per spec §7.1 and the plan's Step 3/4: **positions flip, UVs do
not.** Vertex positions are `Vec3::new(x_px / PPU, -y_px / PPU, 0.0)`
(pixel-space Y negated into world-space Y-up); UVs are `(x_px / W, y_px / H)`
unchanged. The texture (`top_marker.png`, generated by `build.rs`) has a red
strip and the word "TOP" near pixel-row 0 (top of the source image) and a
green strip near the bottom. Whether "TOP" actually renders right-side-up at
the top of the quad on screen is a **visual check — see the user checklist.**
The code implements the plan's asserted convention; it has not been
falsified, but "the code does what the spec says" and "the screen shows what
a human expects" are different claims and only the second is fully verified
by a human.

## What happens at 257 joints?

**Neither a panic, a wgpu validation error, nor any warning-level log
line.** Ran with `RUST_LOG=wgpu_core=warn,bevy_render=warn,bevy_pbr=warn,bevy_animation=warn`
at both 256 and 257 joints; grepping the output for `warn|error|panic|assert`
returned nothing at either joint count, and both runs completed their
`--auto-close` cycle normally:

```
$ m0-1-skinned-mesh.exe --auto-close 60 --joints 256
[m0-1] built mesh: 900 vertices, 1682 triangles, 256 joints
[m0-1] FPS: avg=384.00 smoothed=395.37
[m0-1] FRAME_TIME_MS: avg=4.6947 smoothed=2.5539
[m0-1] auto-close at frame 60, exiting

$ m0-1-skinned-mesh.exe --auto-close 60 --joints 257
[m0-1] built mesh: 900 vertices, 1682 triangles, 257 joints
[m0-1] FPS: avg=384.76 smoothed=408.00
[m0-1] FRAME_TIME_MS: avg=4.3721 smoothed=2.4766
[m0-1] auto-close at frame 60, exiting
```

**Why this differs from the plan's assumption of a hard 256-joint ceiling:**
reading `bevy_pbr-0.19.1/src/render/skin.rs`, `MAX_JOINTS = 256` is real, but
it is the size of the **fallback uniform-buffer path**
(`skins_use_uniform_buffers()` returns
`bevy_render::storage_buffers_are_unsupported(limits)`). On hardware that
supports storage buffers — this machine, an RTX 4080 SUPER on Vulkan — Bevy
uses a growable storage-buffer allocator (`SkinUniforms::allocator`,
`JOINTS_PER_ALLOCATION_UNIT`) instead, which is not capped at 256 joints per
mesh. The only failure path visible in source is
`SkinUniforms::allocator.allocate(...)` returning `None`, which logs
`error!("Out of space for skin: ...")` — that did not trigger at 257.

**Consequence for the M1 validator:** a hard "max 256 joints" client-side
check would be *wrong* on capable GPUs (this one) and *silently wrong* on
uniform-buffer-only GPUs (where the failure mode still needs to be
independently verified — this spike did not have access to non-storage-buffer
hardware to test that path). **This delta from the plan's sketch should be
escalated to the M1 plan**: the safe, portable answer is not "cap at 256" but
"probe `WgpuLimits`/`skins_use_uniform_buffers` at runtime, or accept that the
ceiling is hardware-dependent and test failure gracefully rather than
pre-emptively blocking joint counts that may work fine."

## Frame time at 50 puppets x 40 joints, and the animation/render split

All figures are `--auto-close 300`, uncapped present mode, averaged over the
run (`FrameTimeDiagnosticsPlugin`, `avg`/`smoothed` from the diagnostic
store):

| Scene | FPS avg | Frame time avg (ms) |
|---|---|---|
| 1 puppet, 40 joints, animated | 395.67 | 2.5528 |
| 50 puppets x 40 joints, animated | 401.48 | 2.5052 |
| 50 puppets x 40 joints, joint-driver system disabled (`--no-animate`) | 406.77 | 2.4762 |

Raw output:

```
=== single puppet, animated ===
[m0-1] FPS: avg=395.67 smoothed=409.53
[m0-1] FRAME_TIME_MS: avg=2.5528 smoothed=2.4557

=== 50 puppets, animated ===
[m0-1] FPS: avg=401.48 smoothed=407.37
[m0-1] FRAME_TIME_MS: avg=2.5052 smoothed=2.4665

=== 50 puppets, no-animate (render-only cost) ===
[m0-1] FPS: avg=406.77 smoothed=415.96
[m0-1] FRAME_TIME_MS: avg=2.4762 smoothed=2.4203
```

**Reading this honestly:** the delta between 1 puppet and 50 puppets
(2.55ms -> 2.51ms) and between animated and non-animated 50-puppet runs
(2.51ms -> 2.48ms) is within noise on this GPU — 50 puppets x 40 joints x
900 vertices is not a meaningful load for an RTX 4080 SUPER, and the CPU cost
of the sine-wave `Transform` update system across 2000 joint entities is not
separable from frame-to-frame jitter at this scale. **The honest conclusion
is: 50 puppets at this complexity is nowhere near a bottleneck on
discretely-GPU'd hardware; this spike does not establish a cost model for
weaker hardware (integrated GPUs, older laptops) because none was available
to test on.**

## Delta from the plan's API sketch

- `RenderAssetUsages` is `bevy::asset::RenderAssetUsages`, not
  `bevy::render::render_asset::RenderAssetUsages` (the latter path is
  private in 0.19.1).
- Ambient light is `bevy::light::GlobalAmbientLight` inserted as a
  `Resource`, not a component named `AmbientLight`.
- `WindowResolution` has no `From<(f32, f32)>`; use `(u32, u32)` or
  `WindowResolution::new`.
- `Mesh::with_generated_skinned_mesh_bounds()` consumes `self` and returns
  `Result<Mesh, _>` (confirmed against Bevy's own
  `examples/animation/custom_skinned_mesh.rs`, which calls `.unwrap()`);
  this spike clones before calling it since the code needs the un-bounded
  mesh in the `--no-bounds-fix` branch too.
- Bevy's default `AssetServer` resolves relative to the **executable's**
  directory, not the process's current working directory. Running from
  `spikes/m0_1_skinned_mesh/` failed to find `assets/top_marker.png` — the
  asset had to be copied next to `target/release/m0-1-skinned-mesh.exe`
  (`spikes/target/release/assets/`). **Note for the user:** if you run the
  binary from a different `target-dir` layout, copy
  `spikes/m0_1_skinned_mesh/assets/top_marker.png` to
  `<target-dir>/release/assets/top_marker.png` first, or the puppet will
  render untextured (magenta/white) with an `ERROR bevy_asset::server: Path
  not found` log line — that in itself is useful confirmation that the
  code path is exercised correctly, just pointed at the wrong directory.

## Anything surprising

- The 256/257 joint ceiling is **hardware-dependent**, not a fixed constant,
  because Bevy 0.19.1 picks between a uniform-buffer skinning path (hard
  256 cap) and a storage-buffer path (much larger, allocator-based) based on
  `WgpuLimits`. This was not visible from the plan's sketch and only shows up
  by reading `bevy_pbr::render::skin` source directly.
- `with_generated_skinned_mesh_bounds()` is fallible (`Result`), not the
  infallible builder-chain method the plan's prose implies; the spike logs
  and falls back to the un-bounded mesh rather than panicking, so the
  `--no-bounds-fix` A/B test (Step 5) still runs even if bounds generation
  ever fails for a future mesh shape.

## User checklist — must be verified by eyes on the running window

Run: `cargo run --release --manifest-path spikes/m0_1_skinned_mesh/Cargo.toml`
(no flags — this opens the window and leaves it running; press Alt+F4 or
close the window when done).

- [ ] **TOP orientation.** The word "TOP" (white blocky letters) must appear
      near the **top edge** of the quad, right-side up, not mirrored, with
      the red strip above it and the green strip below. If it appears at the
      bottom, or upside-down, or mirrored left-right, the position/UV
      convention is backwards — note exactly what you see (which edge, which
      orientation).
- [ ] **Wave animation.** The grid should visibly ripple/wave as the camera
      slowly auto-orbits (no input needed — the spike orbits the camera on
      its own).
- [ ] **Culling fix, step 5 of Task 2.** Run once normally (bounds fix on)
      and once with `-- --no-bounds-fix`. In both cases, watch the mesh as
      the camera auto-orbits around it for at least one full 360-degree
      cycle (~25 seconds at the spike's orbit speed). Record: does the mesh
      ever incorrectly vanish (get frustum-culled) with `--no-bounds-fix`
      that it does not vanish with bounds-fix on? The spike cannot detect
      "did the mesh disappear" without eyes on the frame buffer.
  - [ ] With bounds fix (default): mesh stays visible through the full orbit — yes/no?
  - [ ] With `--no-bounds-fix`: mesh disappears at some orbit angle — yes/no? If yes, roughly which angle/distance?
- [ ] **50-puppet stress visual sanity.** Run with `-- --stress` and confirm
      all 50 puppets are visible, laid out in a grid, and all animate
      independently (not in lockstep) — the measured frame-time numbers
      above assume the scene is actually rendering 50 distinct puppets, not
      silently culling most of them.
